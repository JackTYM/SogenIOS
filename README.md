# sogen iOS app shell (Phase 1)

An ordinary iOS app that embeds `sogen::windows_emulator` with the Unicorn backend and runs the
`native-gpu-clear-sample` Windows guest inside it, presenting frames through a `CALayer`.

No JIT, no entitlements beyond ordinary personal-team signing, no app extensions. See
`docs/superpowers/specs/2026-09-04-ios-app-shell-phase1-design.md` for the design and
`docs/superpowers/plans/2026-09-04-ios-app-shell-phase1.md` for how it was built.

## One-time host setup

```sh
brew install xcodegen mingw-w64
# Static sogen libraries for both SDKs:
cmake --workflow --preset=ios-embed-device
cmake --workflow --preset=ios-embed-simulator
# Minimal emulation root (~1.8 GB) + the 32-bit guest PE:
tools/stage-ios-emulation-root.sh
```

## Build

```sh
cd tools/sogen-ios
mkdir -p Resources
cp ../../build/ios-root/native-gpu-clear-sample.exe Resources/
cp ../../build/ios-root/mouse-input-test-sample.exe Resources/
xcodegen generate
xcodebuild -project SogenIOS.xcodeproj -scheme SogenIOS -sdk iphonesimulator \
  -configuration Debug -destination 'generic/platform=iOS Simulator' -derivedDataPath build build
```

The `.xcodeproj` is generated by xcodegen and is gitignored — edit `project.yml`, never the project
file. CMake and Xcode stay decoupled: Xcode never invokes CMake, it just links the archives the
`ios-embed-*` presets already produced.

## Provision the emulation root

The root is ~1.8 GB and is deliberately **not** bundled in the `.app`; it is copied into the app's
Documents container instead. The app looks for `<Documents>/root` and reports a visible on-screen
error if `filesys/` or `registry/` is missing there.

Simulator:
```sh
xcrun simctl install booted build/Build/Products/Debug-iphonesimulator/SogenIOS.app
xcrun simctl launch booted com.jacksonyarger.sogenios && xcrun simctl terminate booted com.jacksonyarger.sogenios
DATA=$(xcrun simctl get_app_container booted com.jacksonyarger.sogenios data)
rsync -a --delete ../../build/ios-root/ "$DATA/Documents/root/"
```

Device:
```sh
xcrun devicectl device install app --device <udid> \
  build/Build/Products/Debug-iphoneos/SogenIOS.app
xcrun devicectl device copy to --device <udid> \
  --domain-type appDataContainer --domain-identifier com.jacksonyarger.sogenios \
  --source ../../build/ios-root --destination Documents/root
```

`UIFileSharingEnabled` is set, so dragging `build/ios-root` in as `root` via Finder's device file
sharing is an equivalent fallback if `devicectl copy to` misbehaves.

## Run

`xcrun simctl launch --console-pty booted com.jacksonyarger.sogenios`

Expected: the view cycles blue → green → red → yellow → cyan → magenta → orange → violet at 400 ms
per frame and holds violet; the log ends with `[ngcs] done`. Tapping the view logs
`[ios-ui] delivering raw mouse input flags=0x0001` / `0x0002`.

Note: the `[ngcs]`/`[sogen]` log lines only appear in the **on-screen** log, not in the
`simctl launch --console-pty` console output — `SogenBridge.mm`'s `appendLog` routes through the
Swift `onLogLine` closure once `ContentView` sets it, bypassing `NSLog`/stdout entirely. Read the
log on the simulator screen (or via a screenshot) rather than grepping console output.

## JIT grant (Task 8)

Task 7 found that `windows_emulator` on the Unicorn backend crashes on **real hardware** (not the
Simulator) the moment the guest needs a genuinely new Unicorn TCG JIT-buffer translation:
`EXC_BAD_ACCESS`/`SIGKILL`, `KERN_PROTECTION_FAILURE` at a 128MB `VM_ALLOCATE` region,
`CODESIGNING: Invalid Page` — entirely inside Unicorn's own vCPU-resume path. Unicorn's TCG is a
JIT (x86 → ARM64), and on A18-class (TXM/SPTM) hardware plain `CS_DEBUGGED` is not enough to allow
a W→X transition; a `brk #0xf00d` breakpoint-protocol negotiation is required per the JIT26
mechanism proven end-to-end in this session's out-of-tree spike
(`.worktrees/ios-jit-test/tools/ios-jit-test/`, branch `spike/ios-jit-self-attach`).

Task 8 ported that architecture in: `Sources/JIT/` (`JIT26.{c,h}`, `JITExec.{c,h}`,
`JITSelfAttach.{c,h}`, `JITCoordinator.swift`, `JITExtensionPoint.swift`, `TunnelManager.swift`,
`JITGate.swift`, `JITBridge/JITMessage.swift`), `HelperExtension/` (an ExtensionKit
`extensionkit-extension` embedding StikJIT), `TunnelExtension/` (an `NEPacketTunnelProvider`), and
`Vendor/StikJIT-src` (StikJIT, MPL-2.0, vendored from source — see `Vendor/StikJIT-src/README.md`
for the same source in the spike). `ContentView.swift` now requires a pairing file (imported via
the on-screen "Import Pairing File" button, same device-scoped file the spike/StikDebug uses — see
https://github.com/StikDebug/StikDebug-Guide/blob/main/pairing_file.md) and runs the JIT-grant
sequence (`JITGateOrchestrator.run`) before ever constructing `windows_emulator`. A missing pairing
file or a failed grant is surfaced as a visible on-screen `ERROR:` line; the emulator is never
started in that case, avoiding a guaranteed crash.

**Known blocker (unresolved as of Task 8): `TunnelExtension` cannot be signed under an ordinary
personal-team account.** It requires the `com.apple.developer.networking.networkextension`
entitlement, which Apple does not grant to free personal-team accounts. Confirmed with real,
first-party evidence against Jackson's own account ("Jackson Yarger", team `94CPX5P8X2`):

```
error: Cannot create a iOS App Development provisioning profile for
"com.jacksonyarger.sogenios.TunnelExtension". Personal development teams,
including "Jackson Yarger", do not support the Network Extensions capability.
```

This matches the spike's own README, which never got `TunnelExtension` signed under a personal
team either — only under a separate paid Apple Developer Program account ("ArcticSign"). With
`TunnelExtension`'s embed dropped, the rest of the app (host + `JITHelper` + `StikJIT`) builds,
signs, installs and launches cleanly under the personal team; `JITGateOrchestrator` reaches
`TunnelManager.ensureConnected` and fails there without a running tunnel, which is the expected,
visibly-logged (not crashing) behavior. Resolving this needs one of:
- a paid Apple Developer Program account with the Network Extensions capability approved, used as
  `DEVELOPMENT_TEAM` for at least the `TunnelExtension` target, or
- dropping `TunnelExtension` and relying on a separately-installed, independently-running tunnel
  app (e.g. StosVPN) providing the same loopback route, sacrificing full self-containment, or
- an unsigned build (`CODE_SIGNING_ALLOWED=NO VALIDATE_PRODUCT=NO`) sideloaded via a third-party
  signer under an account that has the capability — outside the normal personal-team `xcodebuild`
  flow.

The actual tap-crash-fix repro (tap the emulator view while the guest runs, confirm no
`CODESIGNING`/`KERN_PROTECTION_FAILURE` crash) has **not** been re-verified end-to-end, because it
needs both a resolved `TunnelExtension` signing path and a real pairing file for this device.
